# GoWay routing engine

The OSRM-shaped hole in GoWay used to be filled by a straight line. This
directory is what fills it properly: **GoWay's own Valhalla deployment**, built
from an OpenStreetMap extract, running on the same ECS cluster as the API.

It is not a Bun workspace, exactly like `packages/reconstruction-worker`: what
it produces is a container image and a set of routing tiles, not a TypeScript
package. Nothing in `packages/backend` imports from here — the backend reaches
the engine over HTTP through `RoutingProvider`, and `ROUTING_VALHALLA_URL` is
the only thing that connects the two.

## Why GoWay runs its own

`packages/backend/.env.example` has said it from the start, and it is not
negotiable:

> A public community Valhalla instance is usable for LOCAL DEVELOPMENT […] it
> is rate limited under a fair-use policy, it is **NOT** an SLA-backed
> production dependency, and consumer applications must never be pointed at
> one. Production runs its own deployment.

`https://valhalla1.openstreetmap.de/route` is volunteer-funded infrastructure
for the OSM community. Pointing `goway.to` at it would be taking somebody
else's donated CPU for a product, and it would make GoWay's directions as
reliable as a stranger's fair-use policy.

## What is in the image

```
/data/tiles.tar          the routing tiles, one mmap-able archive
/data/timezones.sqlite   local time for time-dependent costing
/data/admins.sqlite      country/region rules: driving side, access, speed units
/data/valhalla.json      the engine configuration, generated by build-tiles.sh
```

The tiles are BAKED IN rather than mounted from EFS or pulled from S3 at
start-up, and that is a deliberate trade:

  * A task is immutable and self-contained. There is no start-up download to
    fail, no shared filesystem to run out of burst credits, and rolling back
    the engine is rolling back an image tag.
  * The cost is a ~2 GB image and a slower cold start (ECR → Fargate, inside
    the region, about a minute).
  * The thing it rules out is the failure mode where an engine comes up
    healthy, answers `/status`, and routes nothing because its tile volume did
    not mount. A route request against a tile-less Valhalla is not an error —
    it is `no route found`, which the app renders as a legitimate answer. An
    engine that lies about coverage is the same defect as a straight line.

## Coverage: Spain first, and why not the planet

`REGION` defaults to `europe/spain` (a Geofabrik extract path). Measured on a
32-core workstation, 2026-09-20:

| Region | Extract | Tile build | `tiles.tar` | Image in ECR |
| --- | --- | --- | --- | --- |
| `europe/spain` | 1.48 GB | **4m 43s** | 2.07 GB | 1.23 GB |

The image column is what ECR bills, which is the COMPRESSED size — 2.3 GB of
tiles and databases on disk, 1.23 GB over the wire and at rest.

The planet is roughly 80 GB of extract and 25–30× this in tiles, wants tens of
GB of RAM to build, and would not fit the Fargate task below at any size worth
paying for. Spain is where GoWay's users, its fixtures and its first Places
are; the next region is a `REGION` change and a re-run, not a redesign.

**A route that leaves the covered region is answered honestly.** Valhalla
returns "no suitable edges near location" or "locations in unconnected
regions"; `packages/backend/src/routing/valhalla.ts` maps both to an EMPTY
route list, the SDK and the app render that as "no route between these stops",
and nothing draws a line. Coverage that stops at a border is a known limit, not
a lie.

## Building tiles

```bash
# All of Spain, into ./build. Needs docker and ~12 GB of free disk.
./build-tiles.sh

# Somewhere else. Any path under https://download.geofabrik.de/.
REGION=europe/portugal ./build-tiles.sh
REGION=europe/spain/cataluna ./build-tiles.sh   # much faster, for iterating
```

Then the image:

```bash
docker build --platform linux/arm64 -t oxy/goway-routing:latest .
```

`--platform linux/arm64` because `oxy-cluster` is Graviton. There is no `RUN`
step in the Dockerfile, so nothing is emulated when you build it on an x86
laptop — the layers are a `COPY` of data onto the upstream arm64 image, and
**Valhalla tiles are architecture-independent** (little-endian, and both
platforms are), so tiles built on x86 serve correctly on arm64.

In CI this is `.github/workflows/build-routing-tiles.yml`, which does all of
the above on a native arm64 runner and pushes to ECR. That workflow is the
supported path: OSM changes every day, and a routing engine nobody rebuilds is
a map that quietly ages.

## Running it locally

```bash
docker run --rm -p 8002:8002 oxy/goway-routing:latest
# then, in packages/backend/.env
ROUTING_VALHALLA_URL=http://127.0.0.1:8002/route
```

## What it costs

One Fargate ARM task, us-west-2, on-demand, 730 h/month:

| Size | vCPU-hours | GB-hours | **Per month** |
| --- | --- | --- | --- |
| 1 vCPU / 4 GB | $23.64 | $10.38 | **$34.02** |
| 2 vCPU / 8 GB | $47.28 | $20.77 | **$68.05** |

at $0.032384 per vCPU-hour and $0.003556 per GB-hour. Plus ECR storage: 1.23 GB
× $0.10/GB-month × 3 retained images ≈ **$0.37**. No ALB (it is registered in
Cloud Map and never leaves the VPC), no NAT (same subnets as the API), no data
transfer (same AZ).

**Total: about $34.40 a month.** If that is too much, the cheaper shapes, in
order: run `europe/spain/cataluna` tiles on 0.5 vCPU / 2 GB (~$17), or set
`desired_count` to 0 between demos — the tiles live in the image, so bringing
it back is a number, not a rebuild. Routing then answers
`provider_unavailable`, which the app renders honestly rather than as a line.

**GoWay runs the 1 vCPU / 4 GB size, at about $34/month.** Valhalla mmaps
`tiles.tar` and lets the page cache do the work, so memory is a performance
knob and not a correctness one; Spain's 2 GB of tiles fit inside 4 GB with room
for the working set. A Barcelona→Madrid `auto` route — 621 km, 27 maneuvers —
answers in well under a second warm.

Raise it to 2/8 when p99 latency says to, and raise `desired_count` before
raising the size: two small tasks survive an AZ event and one big one does not.
